# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Frunchy is a social stats site for anime: it ingests a user's Crunchyroll watch history (sent by the sibling `../browser-extension` Svelte extension) and builds statistics, and later an "anime DNA" profile, from it. This repo is the F# backend, which also server-renders the web UI in English (default) or Spanish.

The guiding principle (see `README.md` and `.specify/memory/constitution.md`) is to keep it simple: **watch history is the core asset**, and the code deliberately avoids queues, event sourcing, CQRS, and frameworks like Wolverine/Hangfire until real usage justifies them. Don't add that kind of infrastructure unless asked. Features go through spec-kit (`specs/###-name/`: spec → plan → tasks → implement); feature 001 is in `specs/001-crunchyroll-history-import/`.

## Architecture

**Load the `oxpecker` skill** (`.claude/skills/oxpecker/`) before touching routes, handlers, views, htmx or Alpine. It covers the API, the upstream examples, and which documented features the pinned package versions **don't** have (the upstream docs track a newer `develop` branch).

**Vertical slices: one file per endpoint in `Handlers/`.** Each slice is laid out top to bottom as: view (`HtmlElement` functions piped into `Views.Layout.page texts title`; for JSON endpoints this section holds the request/response records, whose field names *are* the camelCase wire names) → `private` data-access functions with the slice's own SQL → `handler` → `let endpoint = GET [ route "/path" handler ]` with an explicit verb. Templates: `Handlers/Users/Dashboard.fs` (HTML) and `Handlers/Api/CreateImport.fs` (JSON). Operator commands follow the same idea, one file each in `Operations/`. `Program.fs` is only the composition root: `configureServices`, `configureApp` (localization, error/404 handlers), `endpoints`, CLI dispatch, and `buildApp`, which the tests reuse on a TestServer.

**F# compile order matters.** Files compile in the order listed in `FrunchyBackend.fsproj`: Domains → Infrastructure → Views → Handlers → Operations → Workers → Program. Add each new file in its place.

**Routes**:
- `GET /healthz` (feature 016, `Handlers/Health.fs`, the first file of the Handlers section): always mapped, plain text, `Cache-Control: no-store`, no cookie, no rate limit. See the Commands section for the rest of the feature.
- `GET /` (home) and `GET /u/{username}`: the public dashboard. Figures are computed by SQL at request time from `watch_events`.
- `GET /u/{username}/dna` (feature 004, `Handlers/Users/Dna.fs`): the Anime DNA, one SQL statement at request time over deduplicated minutes (a dub and its original count once), shown from 15 fully watched episodes; its totals repeat the dashboard's query on purpose and a test pins them equal.
- `GET /u/{username}/year/{year}` and `/u/{username}/year` (feature 005, `Handlers/Users/Year.fs`): one UTC calendar year with the DNA page's rules (totals undeduplicated so the years add up to the dashboard; MyAnimeList figures deduplicated). A year counts an episode by its latest watch, the only one stored. The figure helpers both pages use (`figureSection`, `shareLine`, `coverageNote`, `notEnough`, `yearPicker`…) live in `Views/Components.fs`.
- `GET /u/{username}/anime/{seriesId}` (feature 006, `Handlers/Users/Anime.fs`): one series for one user, a row per watched episode folded in F# (the dashboard's totals rule). The id is checked against `^[A-Z0-9]{6,20}$` before any query. Seasons sharing a MyAnimeList entry show its details once. Every series title on the dashboard, DNA and year pages goes through `Components.seriesLink` (`data-series-link`).
- `GET /review/mal`, `GET /review/mal/manual`, `POST /review/mal/set|none|retry|auto` (feature 007, `Handlers/Review/MalReview.fs`): operators review MyAnimeList matches. An operator is the root (the signed-in user whose username equals `Frunchy:RootOperator`, read per request, trimmed, case-insensitive, empty = no root) or a signed-in user with a row in the `operators` table (the flag rides along with `WebAuth.validatePrincipal`'s one user query; `WebAuth.isOperator` = `isRoot` or the flag). `Frunchy:Operators` is retired and grants nothing. **Every review handler is wrapped in `Layout.requireOperator`, outermost, before any form is read**: outsiders get the plain 404 page (never a redirect) on every route and verb, and the `review-write` limiter (30 POSTs a minute per IP) counts operators only, so an outsider never sees a 429. Writes go through `Infrastructure/MalActions.fs` (shared with the CLI; `Expect.Open`/`Manual` checks the row under `FOR UPDATE` in the write's transaction), validate input first, record a `mal_*` security event and redirect with `?msg=<key>`. The web retry passes the season id.
- `GET /review/operators`, `POST /review/operators/add|remove` (feature 008, `Handlers/Review/Operators.fs`): the root manages operators. **Every handler is wrapped in `Layout.requireRoot`, outermost** (shares `requireOperator`'s 404: operators who aren't root, regular users and visitors get the plain 404 on every route and verb, and with no root configured nobody gets in). A POST then needs `WebAuth.requireFresh "/review/operators"`, then `readValidatedForm`, then `Username.tryCreate` (invalid → `?msg=bad-input`, no query), then `Infrastructure/OperatorActions.fs` (shared with the CLI `operator-add|remove|list`; the change and its events share one transaction), then an information log line naming both users and a redirect with `?msg=<key>`. The root's username is never added or removed (`IsRoot`). Events: `operator_added`/`operator_removed` on the affected user's account as `Actor.Operator`, plus, from the web only, on the root's account as `Actor.User`. The `operators-write` limiter (10 POSTs a minute per IP) counts the root only, so an outsider never sees a 429.
- `GET /review/invites`, `POST /review/invites/create|revoke` (feature 019, `Handlers/Review/Invites.fs`): operators (root or table, like `/review/mal`) create, list and revoke sign-up invites. **Every handler is wrapped in `Layout.requireOperator`, outermost** (visitors and regular users get the plain 404 on every route and verb, before any form is read), the POSTs use the `review-write` limiter (operators only, so an outsider never sees a 429), then `readValidatedForm` and the input rule (`days` plain digits 1 to 365, else `?msg=bad-days`; `id` a Guid, else `?msg=bad-input`). The work is `Infrastructure/InviteActions.fs` (`create`, `list`, `revoke`), shared with the CLI's `invite-create|list|revoke` (`Operations/Invite*.fs` are thin wrappers with unchanged output; each takes an optional operator id that records `invite_created`/`invite_revoked` on that account as `Actor.User` in the change's transaction; the CLI passes none). **The code appears only in the response of `POST /review/invites/create`** (a 200 page, no redirect, `Cache-Control: no-store`, `data-invite-code` and a copy button); only its hash is stored, and it is never in a URL, redirect, log line or security event (a test checks the database, events and captured logs). Revoke is one conditional `UPDATE` (active only), so two operators racing get one `revoked` and one `not-active`. The page lists the 100 newest (`data-invite-row`, `data-invite-state`, `data-invite-used-by`); `/account` links to it for operators (`data-invites-link`). No schema change: `invites` has no creator column, the event is the record.
- `GET /anime/{seriesId}/episode/{episodeId}` (feature 009, `Handlers/Episodes/Episode.fs`): the public page of one catalog episode, not of a person (details, Crunchyroll and MyAnimeList links, and its comment thread). Both ids are checked against `^[A-Z0-9]{6,20}$` before any query; unknown or unresolved episodes get the plain 404. A dub and its original share one thread, computed per request with the DNA key (the original season, `shared_from`, plus the episode number); a comment stays on the episode it was written on (`data-episode`). `POST …/comments` needs a sign-in (`requireSignedInReturning`), takes a form-minted `id` (insert `ON CONFLICT DO NOTHING`, so a double submit stores one comment), `content` (`Infrastructure/CommentRules.fs`: trimmed, 1 to 2,000 characters, the spoiler warning text) and `spoiler`. `GET/POST /comments/{id}/edit` and `POST /comments/{id}/delete` are the author's only: the author lookup runs before the form is read, and everyone else (signed out included) gets the plain 404. Delete is a tombstone (`deleted_at`), so ids are never reused. `POST /comments/{id}/hide|unhide` (`Handlers/Episodes/HideComment.fs`) are wrapped in `Layout.requireOperator`, outermost, use the `review-write` limiter and record `comment_hidden`/`comment_unhidden` events on both accounts (the author's as `Actor.Operator`, the operator's as `Actor.User`); hiding hides on Frunchy only. The `comments` table is shaped for Megáfono 002 (see `docs/fediverse.md`): the fediverse columns (`remote_actor`, `object_id`, `in_reply_to`, `audience`…) are filled by feature 015: `object_id` when a Frunchy comment is published, the rest by remote replies.
- `GET /u/{username}/compare` (feature 011, `Handlers/Users/Compare.fs`): taste compatibility between the signed-in viewer and one person. Order: `WebAuth.requireSignedIn` (signed out goes to `/signin?returnUrl=…`), then the username (invalid or unknown: the plain 404), then self (redirects to the dashboard), then `Compatibility.load`. The same figures show as a card on `/u/{username}` for a **signed-in non-owner only** (`Dashboard.fs`; anyone else, and the owner, costs no compatibility query). `Infrastructure/Compatibility.fs` runs two statements on the DNA page's dedup rules (a dub and its original count once) and is symmetric: the score is the average of the shared series over the smaller history (scaled down while that history has fewer than 10 series) and the cosine similarity of the genre shares (shared series alone when no genres), shown as 5 levels in words (Low, Some, Good, High, Very high), **never a percentage or raw score, not even in an attribute**. Each person needs 15 fully watched episodes for a level, otherwise the card and page say whose history is short. Meter and bars are `Components.levelMeter` / `toneBar` (amber is the viewer, rose the other person). Hooks: `contracts/compatibility.md`.
- `GET /charts`, `/charts/season`, `/charts/all` (feature 012, `Handlers/Charts/Charts.fs`, public): what Frunchy is watching. Ranking by people (distinct users with at least one resolved episode watched in the window), then episodes, title and series id; 20 rows. **The privacy minimum** `Frunchy:Charts:MinPeople` (default 3, never below 2; `Charts.minPeople`) is applied in SQL (`HAVING`), and it also gates "Watched by N people on Frunchy" on the anime page and the episode page (an episode counts its dub group); no chart or count names a person. Windows: week (the last 7 days), season (the current UTC quarter: Winter, Spring, Summer, Fall) and all time. The week chart adds movement against the previous 7 days and an 8-week inline-SVG trend (numbers only, never user text). The all-time rows are kept 10 minutes in `IMemoryCache`; `mine` (the viewer's own anime-page link) is computed per request and never cached. SQL and pure functions in `Infrastructure/Charts.fs`; the `ix_watch_events_watched` index serves the windows. Hooks: `contracts/charts.md`.
- `GET /anime/{seriesId}` (feature 013, `Handlers/Series/Series.fs`, public): the page of one series, not of a person. The id is checked against `^[A-Z0-9]{6,20}$` before any query; unknown series and series with no episode of known length get the plain 404. One statement loads a row per known episode with its season, match, MyAnimeList entry and comment count, folded in F# into seasons the anime page's way (Crunchyroll's season order, the seasonless last; MyAnimeList details once per shared entry, later seasons a compact link; the comment count uses the thread's visibility, public or unlisted and not deleted, hidden ones counted). People "Watched by N" (all time) and "this week" are gated by `Frunchy:Charts:MinPeople` like the charts (`Charts.seriesPeople`, `Charts.seriesPeopleSince`); no person is named. Seasons over 30 known episodes start closed in a native `<details>` (One Piece has 1,000+). Links to it (`data-series-page-link`): the chart row title for everyone, plus a separate "Your history" link (`data-chart-mine`) to the viewer's own anime page when they watched it; the episode page's series title; the anime page. Hooks: `contracts/series-page.md`.
- **Usernames** (feature 013): new ones (sign-up, `user-create`) go through `Username.tryCreateNew`, which also refuses a trailing `-` (Mastodon refuses such remote usernames); every lookup keeps `Username.tryCreate`, so an existing name ending in `-` still works.
- Federation (feature 015, only with `Frunchy:Federation:Enabled`; with it off every route below is absent and answers the plain 404, nothing is queued and no page shows a handle). `GET /megafono/actors?handle=` and `/megafono/actors/{id}` (`Handlers/Megafono/Actors.fs`) are Megáfono's actor lookup (users by `users.id`, series as `series-{seriesId}` with a lazily made handle) and `POST /megafono/webhooks` (`Handlers/Megafono/Webhooks.fs`) receives its events (bearer plus `Megafono-Signature`, raw body read first and capped at 1 MB, events deduplicated by id in `megafono_events`, remote replies stored as `comments` rows and shown as text only). Every call Frunchy makes to Megáfono for threads, comments and accounts goes through the Postgres outbox `fediverse_outbox` (`Fediverse.enqueue`, written in the change's own transaction) and `Workers/FediverseOutbox.fs` (`processNext`, switch `Frunchy:FediverseWorkerEnabled`, default true, which the tests turn off like the other workers); `Infrastructure/MegafonoClient.fs` is the "megafono" `HttpClient` (no Polly: the outbox retries). Block management is the one synchronous exception (`Infrastructure/BlockActions.fs`, shared by the two pages below): `POST /account/blocks/add|remove` (`Handlers/Account/Blocks.fs`; `requireSignedIn`, `readValidatedForm`, `account-write`; the list is rendered inside `/account#blocks`, read from Megáfono at render, and a failed read shows a plain line instead of failing the page) and `GET /review/fediverse` plus `POST /review/fediverse/blocks/add|remove` (`Handlers/Review/FediverseBlocks.fs`, instance blocks; **every handler wrapped in `Layout.requireOperator`, outermost**, `review-write` limiter, plain 404 for everyone else). The field takes `@user@host`, `user@host`, an `https://` actor URL or a bare domain (`MegafonoClient.parseBlockTarget`, by shape); every answer comes back as `?msg=block-added|block-already|block-removed|block-not-found|block-not-blocked|block-blocked|block-unreachable|block-invalid|block-error#blocks`, and a `fediverse_block_added|removed` security event is recorded only for a change (201 and 204). The dashboard and the series page show `Follow on the fediverse: @handle@domain` with a copy button (`Components.fediverseHandleLine`, `data-fediverse-handle`) and advertise the actor (`Layout.advertiseActivityPub`: head link plus `Link` header); the episode page does the same for its published thread. `fediverse-status` prints the settings (never a secret), the outbox counts and the oldest waiting item; `series-handle` sets a series handle until its thread is published (exit 0 set, 1 usage or invalid, 2 unknown series, 3 already federated, 4 taken).
- **Private profiles** (feature 017, `Infrastructure/Profiles.fs`): every route under `/u/{username}` (dashboard, DNA, both year routes, anime, compare) answers only the owner, a visitor holding a grant and public profiles; everyone else, operators and the root included, gets **exactly the unknown-user 404** (`Layout.messagePage … UserNotFoundTitle`), so a test compares the bodies. A profile is public when its owner chose `public` (`profile_settings.visibility`), or never chose and `Frunchy:Profiles:DefaultVisibility` is `public`; the setting defaults to `private`, is read once into the `ProfileSettings` singleton and an invalid value stops startup naming the key. **The gate** is `Profiles.gate` (or `forViewer`/`visibleTo`), called right after the handler's user lookup and before any other query (compare: signed in, username, lookup, visibility, self redirect, `Compatibility.load`); the pure rule is `Profiles.canView viewer grants owner`. The owner's private pages show `Components.privateProfileNote` (`data-profile-private`) in place of the copy-link block (`Components.profileAddress`). The owner sets the choice on `/account#visibility` (`Handlers/Account/Visibility.fs`, `POST /account/visibility`; event `profile_visibility_changed`) and has one **share link** (`Handlers/Account/ShareLink.fs`: `POST /account/share-link` creates or replaces it and renders it once with `data-share-link`, like the sync key; `POST /account/share-link/revoke`; only `ShareToken.hash`, a fresh link id and its date are stored; events `share_link_created|replaced|revoked`). `GET /s/{token}` (`Handlers/Share.fs`, `share` limiter, 30 a minute per IP, counts valid and invalid requests): shape check (`ShareToken.isWellFormed`), then the hash; valid → `Profiles.grantAccess` and 303 to `/u/{username}` (the owner is only redirected); invalid → the plain 404 page and **no Set-Cookie**. The grant is the `frunchy.shares` cookie (data-protected, HttpOnly, SameSite=Lax, Secure over https, 30 days, at most 20 entries `{u, l, at}`) naming the user and the **link id**, so replacing or turning off the link ends every browser's access at once; a tampered cookie means no grants. Comment authors on the episode page get `data-comment-author` and an `href` only when `Profiles.canView` (grants read once per request; the comments query joins `profile_settings`); the MyAnimeList review links seasons to `/anime/{seriesId}` (`data-series-page-link`), never into a history. Aggregates (charts, "Watched by N") and `/api/*` are unchanged. **Tests**: the fixture's `createAppWith` sets the default to `public` so the earlier suite keeps opening other users' profiles; the 017 tests pass `private` (or `""`, the app's real default) in `extraConfig`; `ProfileHelpers.fs` has the shared world (private "animenerd", `other`, root `boss`, a signed-out browser) and the account-page helpers. Hooks: `contracts/visibility.md`.

**Ingestion pipeline** (the core flow):
```
extension → POST /api/imports → validate envelope { profileId, pages: [ { url, body, capturedAt } ] }
          → bind/verify the Crunchyroll history owner = (account id from the page URL path, required profileId);
            the URL id is shared by every profile of an account, so profileId keeps profiles apart
          → cr_imports (pending) + cr_import_pages (body stored verbatim as `json`, never modified) → 202
ImportProcessorService → processNext: claim the oldest pending import (FOR UPDATE SKIP LOCKED; stale claims > 10 min retried)
          → Infrastructure/CrunchyrollPage.parsePage classifies each entry: processed / unresolved (no panel) / unsupported / failed
          → upsert shared catalog cr_series / cr_seasons / cr_episodes (freshness-guarded by source_at)
          → upsert watch_events (PK user + episode; replaced only by a strictly newer (watched_at, fully_watched, playhead))
          → issue rows + counts → completed (or failed with error)
```
- **Order-independence and idempotency are invariants.** Re-sending or reordering submissions must give identical results, and `user-rebuild` must reproduce identical figures. Tests enforce both.
- **Series are keyed on the entry's `parent_id`**, so franchise movies count with their series.
- **Unresolved entries** create a stub `cr_episodes` row (no `duration_ms`). They're excluded from the figures until a later page brings the details.
- **Paging fields** (`page` cursor, `total`, `meta`) are opaque and never read.

**Browser auth (feature 002)** uses ASP.NET Core's own handlers: Google (first-party) and Umbral, our self-hosted OpenID Connect provider (separate repo; `AddOpenIdConnect`, code + PKCE, `response_mode=query`, `Authority` in config, https unless loopback). No identity server in this repo. `Infrastructure/WebAuth.fs` holds two cookie schemes:
- `frunchy.external`: 10 minutes, carries `(provider, provider user id)` from the provider callback to `/signin/complete`, which acts in one of 3 modes (signin, link, reconfirm, passed in the challenge properties);
- `frunchy.session`: 30 days sliding, with an `auth_time` claim. Generating a key and deleting the account use `requireFresh`, which needs a sign-in within 10 minutes; otherwise `/signin/reconfirm` sends the user back to the same provider.

More rules:
- **Forms**: every state-changing POST uses `WebAuth.readValidatedForm`, which checks the antiforgery verdict of `UseAntiforgery` first.
- **Rate limits**: per IP, via `RequireRateLimiting` (`signin`, `signup`, `claim`, `account-write`, `comment-write`: 10 comment writes a minute per IP).
- **Sign-up** is invite-only (`invites`, consumed in the same transaction that creates the user).
- **Claiming**: operator-created accounts are claimed with their sync key, only while they have no `user_identities` row.
- **One identity per provider per account.**
- **Security events**: every account action records one in `security_events` (via `Infrastructure/SecurityEvents.record`, in the action's transaction).
- **Shared actions**: `Infrastructure/AccountActions.fs` (regenerate key, reset binding, delete) is shared by the CLI and the web, so they behave identically.

**Data access** is raw Npgsql with hand-written SQL. There's no ORM or repository layer. **Values never go into SQL text**: always pass them as parameters (`@name` + `cmd.Parameters`). SQL text is a literal; the only interpolation allowed is a fixed fragment chosen by our own code, and `tests/FrunchyBackend.Tests/SqlGuardrailTests.fs` fails on anything else (interpolated values, `sprintf`, `"…" + value`, SQL from a variable not on its allowlist). Add new exceptions there with a reason. `DbConfig` is a DI singleton (`ctx.GetService<DbConfig>()`). The schema is the idempotent `initializeSchema` in `Infrastructure/Database.fs`, with no migrations: schema changes go there and into `SCHEMA.md`. Everything personal hangs off `users` with `ON DELETE CASCADE`, and the catalog tables are shared. Raw pages are only ever deleted by `user-delete` (the constitution's single exception).

**Localization**: every user-facing string lives in `Views/Texts.fs` (a typed record with `en` and `es` values). The language comes from `Accept-Language` only. Views never contain literals. ViewEngine writes non-ASCII as `&#NNN;`, so tests decode with `readHtml`. Times are rendered as `<time datetime="…Z" data-fr-time>` with a UTC fallback, and the layout's `Intl` script localizes them in the viewer's time zone.

**MyAnimeList enrichment (feature 003)**: `Workers/Enrichment.fs` matches every `cr_seasons` row to a MyAnimeList entry, without touching the import path (a sweep discovers new seasons). Data comes from MyAnimeList's official API v2 (`Frunchy:Mal:Provider=mal-api`, default; client id `Frunchy:Mal:ClientId` is a secret, kept in Bella as `Frunchy__Mal__ClientId`) or Jikan (`jikan`). Without a client id the worker logs a warning and stays off.
- **Queue**: Postgres. `cr_season_matches` holds one row per season (status, attempts, `next_attempt_at`, claims with `SKIP LOCKED`); `mal_anime.refresh_*` is the refresh queue (30 days, 7 while airing).
- **Provider adapter**: `Infrastructure/MalClient.fs` (`Provider`: paths, query shaping, parser per provider; `MalApiModel.fs` / `JikanModel.fs` parse into the shared records of `MalModel.fs`). Only the adapter knows the provider; the matcher, queue, storage and dashboard don't.
- **Client**: a named `HttpClient` "mal" with a `Microsoft.Extensions.Http.Resilience` pipeline (total timeout → 3 retries honouring `Retry-After` → 1 req/s token bucket → attempt timeout). Register client configuration with an explicit `Action<HttpClient>`: a bare F# lambda resolves to the typed-client overload and is silently ignored.
- **Matching**: `Infrastructure/MalMatching.fs`, pure, deterministic title tiers. The series title finds MyAnimeList's first season (the anchor); other seasons and movies follow its sequel/related links; dubs share their original; no TV sequel at all means every season is the same entry (One Piece, Eyeshield 21). Uncertain → `ambiguous`/`no_match`, never guessed.
- **Data**: provider responses are stored verbatim with their provider (`mal_anime.raw`/`source`, `mal_searches.raw`/`source`), so `mal-rebuild` re-derives everything with zero requests. Rows with `method = 'manual'` are never written by automatic code (`MalCatalog`'s guard).
- **Dashboard**: score, 3 genres and a MyAnimeList link on matched recent cards, plus "Top genres" (fully watched episodes, the "Episodes watched" rule).

**Tests** (`tests/FrunchyBackend.Tests`): one Postgres Testcontainer per run (`max_connections=500`) with a fresh database per test (`PostgresFixture.newApp`).
- **No real provider is ever called**: `Infrastructure/FakeMal.fs` replaces the "mal" client's primary handler (route keys `search:<q>` / `details:<id>`, request log, scripted 429/504/delays) with instant pacing and a fake client id. `MalFixtures.fs` builds MyAnimeList API-shaped bodies and a scripted catalog for some 2026-sample series. `JsonSamples/mal/` holds real responses recorded by the opt-in test in `SampleEnrichmentTests.fs` (`FRUNCHY_RECORD_MAL=1 bella run -- dotnet test --filter-method "*record the 2026 sample*"`, then rebuild: the replay reads the copy in `bin/`); `JsonSamples/jikan/` holds the one recorded Jikan response. `TestApp.Mal` is each app's fake; `enrichAll` runs the worker until idle.
- **`FakeMegafono`** (`Infrastructure/FakeMegafono.fs`) replaces the "megafono" client's primary handler like `FakeMal` does: it records every request, answers with the contract's defaults (publish gives 201 and the same key again 200, blocks kept in memory), and scripts errors per route (`Route`, `FailNext`). `newFederatedApp` / `createFederatedApp` run the app with federation on, and `drainOutbox` drives the outbox worker; no test needs a real Megáfono.
- **Fake providers**: `test` and `test2` (`Infrastructure/FakeProvider.fs`) are registered only by the tests. `GET /signin/test?sub=abc` acts like a provider round trip, and `?fail=1` simulates a cancellation.
- **`Browser`** (`Infrastructure/Browser.fs`) keeps cookies, follows redirects with `Get`, and posts forms with their antiforgery token (`PostForm`).
- **Helpers**: `AuthHelpers.signedUp` / `connectExtension` give a signed-in user with a key.
- **Time**: the 10-minute rule is tested with a `TimeProvider` registered via `createAppWith`. The real app runs on a TestServer with the hosted worker disabled, and tests call `ImportProcessor.processNext` directly (`TestHelpers.processAll`). Fixture builders live in `Fixtures.fs` (`syntheticPages`, `envelopeOf`, …).

**Design system (features 004, 010)**: "Night Broadcast" since feature 010 (`design/night_broadcast/DESIGN.md`, contract `specs/010-night-broadcast/contracts/design-system.md`): warm dark surfaces; Figtree text, Bricolage Grotesque headings (`--font-display`), IBM Plex Mono figures, usernames, keys and URLs. Colour roles: amber (`primary`) is the person the page is about and the primary action, rose (`secondary`) is other people, spoilers and warnings, lilac (`tertiary`) is tags, coral (`error`) is errors. Solid fills only, no gradients; buttons and pills fully rounded. No DaisyUI. Tokens live in `Views/Theme.fs` as CSS custom properties with the **same names and values as the extension's `browser-extension/src/styles/tokens.css`** (`DesignSystemTests` checks parity and WCAG AA contrast), mapped into the Tailwind CDN config; shared components in `Views/Components.fs`; icons are Material Symbols subset to `Theme.Icon` (add a case to use a new one). **Tests read only `data-*` hooks, never classes**; restyles must keep every hook (`specs/004-anime-dna-design-system/contracts/design-system.md`). Changing a shared token means telling the extension session; until it follows, the parity test fails where both repositories sit side by side. UI work goes through the `impeccable` skill (shape → build → audit) and its craft floor (no eyebrow labels, no emoji icons, plain copy).
